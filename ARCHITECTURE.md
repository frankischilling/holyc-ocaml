# holyc-ocaml architecture

The compiler is split into explicit stages. Each stage consumes immutable inputs and returns either a value or structured diagnostics. Sessions own source IDs and configuration; compiler modules do not rely on hidden global state.

The current slice has seven layers:

- `Common` owns source files, byte positions, spans, diagnostics, deterministic rendering, and target-width integer helpers.
- `Frontend` owns token definitions, the audited keyword table, streaming lexical state, canonical include resolution, nested file, definition, and predefined-value frames, `#include`, `#define`, constant `#if` and `#assert` evaluation, mode and symbol conditionals, help-directive metadata, the spanned syntax tree, primitive globals, and bound primitive function prototypes. The declaration parser preserves ordered storage, visibility, and calling modifiers, binding modes and alternate targets, bounded pointer layers, comma-delimited global groups, global array dimensions, named or unnamed parameters, parameter register qualifiers, recursive function-pointer parameter declarators, prototype punctuation, terminal varargs markers, and optional parameter defaults. Default values and array dimensions use one bounded Pratt parser driven by the audited operator table. Its AST distinguishes literals, identifiers, `$$`, grouping, prefix operations, binary operations, an absent default, and an unsized first array dimension. A lexer frame points to its caller, so scanners request only the lookahead bytes they need and can finish a token or trivia item after one or more frame returns. Tokens and trivia store ordered source segments instead of copying the caller suffix into a temporary buffer. The preprocessor expression evaluator uses explicit 64-bit target values and the generated HolyC precedence table. Each preprocessing stream owns its mutable cursors, one-token expression lookahead, conditional stack, current help index, ordered help-file records, selected compilation mode, deterministic date and time settings, command-line source state, generated-byte budget, expression-node budget, and ordered pending diagnostics. The parser adds one bounded token of lookahead and captures include and definition context before it requests the next item. Declaration modifiers, bindings, binding targets, register qualifiers, explicit register names, pointer stars, names, array brackets, delimiters, parentheses, variadic markers, expression operators, and expression terms are explicit AST nodes with their source segments and definition origins. Function-pointer nodes distinguish return pointer layers from declarator indirection and contain the same parameter AST recursively. The parser reads the configured compilation mode before it accepts either import spelling. The session owns source IDs, the source-ordered definition environment, and a typed view of compiler hash entries. Later parser and semantic work can publish declarations to that view between token requests. It is not the final semantic symbol table.
- `Generated` contains deterministic source facts produced only after pinned checksum and table-shape validation.
- `Sema` currently exposes primitive type identity, compiler-option metadata, and the audited function-flag model. Pointer resolution, declaration resolution, conversions, call checking, and aggregate layout have not entered this layer yet.
- `Ir` currently exposes the exhaustive intermediate-code identity and source metadata table. Instructions, control flow, verification, lowering, and execution have not entered this layer yet.
- `Backend` currently exposes the audited TempleOS BIN header, patch-record, relocation, loader-action, and AOT-adjustment specification. It does not contain a serializer, loader, or code emitter yet.
- `Driver` owns compilation sessions, build identity, and deterministic corpus scans. A verified corpus scan checks the reference worktree before and after the run, enumerates the pinned Git tree, and reads committed objects so checkout line endings cannot change its result.

`holyc_lib` exposes the supported high-level entry points. `preprocess_detailed` returns tokens, every diagnostic, and per-stream help metadata so callers can keep nonfatal warnings and compiler annotations together. The older `preprocess` convenience result remains available when only tokens and fatal errors matter. `parse` uses deterministic JIT preprocessing, while `parse_with_config` and `parse_detailed` accept an explicit mode. Ordered `public`, `static`, `interrupt`, `haserrcode`, `argpop`, and `noargpop` prefixes and ordinary or alternate-name bindings retain their source locations but do not alter linkage, storage, or ABI behavior yet. An alternate binding stores its target as a separate source-linked identifier. Either import spelling in JIT mode fails before its declared name is published. Each accepted global is published after its delimiter, and each accepted prototype is published as a function after its semicolon, before the parser requests the next token. A following `#ifdef` can therefore observe either declaration. A detailed parse retains warnings, but any error removes the public AST instead of returning a false success. `Corpus.lex_reference` returns every per-file lexer result and aggregate byte, token, terminator, and payload count. The command-line program uses the same library paths exercised by the CLI golden tests.

Later frontend work will route nonconstant preprocessor expressions and general `#exe` blocks through semantic analysis, verified IR, and the compile-time VM. The current parser accepts direct and comma-separated primitive globals, global array suffixes, and bound primitive prototypes with empty, fixed, or variadic parameter lists, recursive function-pointer parameters, ordered calling modifiers, source-positioned `reg` or `noreg` parameter qualifiers, and core expressions in array dimensions and ordinary or nested parameter defaults. Both `import` and `_import` require AOT mode. Target lookup, alias resolution, `_intern` expressions, `lastclass` defaults, expression evaluation, array layout, initializers, call-site default filling, register allocation, function-pointer globals and members, function-flag validation and ABI effects, unbound function bodies, export behavior, static storage, local and member declarations, general expressions, statements, aggregates, semantic analysis, IR instructions and verification, interpretation, optimization, assembly, hosted code generation, and TempleOS module emission follow in separate changes. A stage enters the supported list only after its verifier boundary and focused tests exist.

## Source authority

TempleOS source at `c26482bb6ad3f80106d28504ec5db3c6a360732c` is authoritative when prose and implementation disagree. `reference/traceability.toml` links each claimed behavior to the pinned function or table, implementation files, and tests.

## Determinism

Byte offsets and source order are preserved. Reports sort data only when source order has no meaning. Version output always names the pinned reference commit. Tests override data that could depend on clocks, locale, process IDs, or temporary directories.
