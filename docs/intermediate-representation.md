# Intermediate-code specification

All source facts on this page refer to TempleOS commit `c26482bb6ad3f80106d28504ec5db3c6a360732c`.

## Opcode registry

`Holyc_lib.Ir_opcode` exposes one constructor for each of the 185 intermediate codes in `Compiler/CompilerA.HH`. Numeric codes cover `0x00` through `0xB8`; `0xB9` is the count sentinel and is not an operation. Lookups by numeric code, `IC_*` constant name, and display name return an option rather than substituting an unknown code.

Each metadata record retains:

- fixed zero-, one-, or two-argument shape, or the variable-argument form;
- result count;
- the source's null, dereference, assignment, or comparison category;
- `fpop` as `pops_float`;
- `not_const` as `prevents_constant_folding`;
- the `IC_*` name and display name separately;
- definition and metadata line numbers.

The field names describe the pinned table and its observed consumers. They are not a complete side-effect model. In particular, `not_const` is preserved because `OptPass012` reads it; it does not claim that every record with `FALSE` can always be folded.

## Checked instruction sequences

`Holyc_lib.Ir_instruction_sequence` is the first executable data model built on that registry. It accepts source-ordered instruction descriptions through one checked constructor. Instruction and value IDs are explicit nonnegative values; list positions and OCaml object identity never become public IDs. Each description carries the checked opcode, ordered value operands, an optional produced value, an independent target type, an optional immediate or reference payload, the original source span when one exists, and the audited `ICF_*` bits from `Kernel/KernelA.HH`. Keeping the target type independent matches `CIntermediateCode.ic_class`, including typed instructions that produce no value.

Construction checks the opcode table's fixed or variable operand shape and exact result count. A produced value must have a target type; a no-result instruction may still carry one. Construction also rejects invalid spans, flag bits outside the pinned fields, duplicate instruction or value IDs, forward uses, and missing definitions. Failures use stable `HCIR0001` through `HCIR0010` codes and retain the offending instruction and span when available. A successful value is immutable and exposes only ordered traversal.

`human` emits the versioned `holyc-ir-v1` form. It uses `IC_*` source names, decimal signed `I64` values, hexadecimal `F64` bit patterns, escaped bytes, resolved symbol IDs, kinds, and names, explicit block payloads, stable instruction and value IDs, target types, flag masks, and source ID plus byte range. The reference commit appears in the header, so a dump cannot be mistaken for a result from a moving TempleOS branch.

## Control-flow classification

`Holyc_lib.Ir_control_flow` assigns every checked opcode one of seven control-flow classes. The explicit identities are `IC_END`, `IC_LABEL`, `IC_JMP`, both switch forms, and `IC_RET`. The 32 codes from `IC_BR_ZERO` through `IC_BR_NOT_BTC` form the conditional branch class. Every other opcode falls through.

The classification keeps three distinctions that matter downstream. `IC_RETURN_VAL` and `IC_RETURN_VAL2` prepare return values but do not return control; the later `IC_RET` does. `IC_SUB_CALL` names a local compiler label but returns to its successor, so it is a fallthrough call rather than a block jump. `IC_END` emits no machine instruction in `OptPass789A`, but it terminates the intermediate-code stream.

Unconditional and conditional branches have one block target. Switches own an ordered target list. Labels, returns, end markers, calls, and ordinary operations have no outgoing block-target payload in this classification. Conditional branches may also fall through; jumps, switches, returns, and the end marker do not.

## Checked block graphs

`Holyc_lib.Ir_block_graph` builds one immutable function graph from source-ordered block descriptions. The caller names the entry block and supplies raw instruction descriptions for each stable block ID. The constructor validates every child sequence before it builds its private block index. It then rejects duplicate block, instruction, or value IDs across the function.

Control-flow payloads follow the classifier. A jump or conditional branch carries one `Block` payload. A switch carries an ordered `Block_targets` payload. A block reference on an opcode with no outgoing target, such as a later label-address operation, remains data and does not become an edge. Every transfer target must name a block in the same graph.

The graph preserves source order even when block IDs are out of numeric order. Ordinary blocks fall through to the next source block. Conditional successors list the explicit target first and the next block second. Switch successors keep first-occurrence target order while removing duplicate destinations from the graph view; the instruction payload keeps the complete ordered list. A final block must end in `IC_END`, `IC_RET`, a jump, or a switch. `IC_END` may appear once and no block or instruction may follow it.

Construction failures use the child `HCIR0001` through `HCIR0010` codes or graph codes `HCIR0011` through `HCIR0020`. Graph errors add the block ID and retain the instruction ID and source span when one exists. `human` emits the `holyc-ir-graph-v1` form with the pinned reference commit, explicit entry, source-ordered blocks, instruction bodies, and derived successors.

## Effect classification

`Holyc_lib.Ir_effects` gives every checked opcode a conservative effect record. Separate access axes cover ordinary memory, stack or frame state, machine registers or flags, port I/O, cache or TLB state, and the timestamp clock. Calls retain local, direct, indirect, import, and extern forms, while inline assembly is an explicit opaque barrier. Each access uses `none`, `read`, `write`, `read-write`, or `opaque`.

The table is reconstructed from `CInit.HC` and the optimizer and backend consumers. It does not pretend that `not_const` means side effect: the generated opcode registry's constant-fold barrier remains a separate field. For example, an absolute address prevents source constant folding but has no runtime effect, while a timestamp read, port input, memory load, or machine-state read is a reorder barrier. Calls and assembly conservatively cover opaque memory and machine state until a later call-summary layer can prove less.

This is an opcode-potential table. It does not yet refine a `MOV`, assignment, or stack operation from final operand modes, model aliases, assign memory regions, or classify exceptions or locks.

## x87 stack discipline

`Holyc_lib.Ir_x87_stack` verifies one checked block graph without changing it. The source table's `fpop` value remains an opcode fact. `ICF_USE_F64`, the three operand and result conversion pairs, `ICF_PUSH_CMP`, `ICF_POP_CMP`, and the three `ICf_DONT_PUSH_FLOAT0` and `ICf_DONT_POP_FLOAT0` bits remain separate instruction inputs.

The verifier orders each instruction's possible floating operations as operand 2 conversion, operand 1 conversion, opcode operation, and result conversion. The three suppression bits address only the operations that survive that ordering. A suppressed push consumes one live x87 value; a suppressed pop leaves one value live. An unused suppression bit, contradictory conversion direction, or more than three addressable operations receives `HCIR0021` instead of an assumed balance. The `IC_PUSH_CMP` result conversion is the source's explicit `FILD` and `FSTP` pair, so it is balanced and does not consume a suppression slot.

Entry depth is zero. The verifier propagates one depth through source-ordered blocks, branch targets, fallthrough edges, and loop backedges. `HCIR0022` reports underflow, `HCIR0023` reports a depth above the x87 limit of eight, and `HCIR0024` reports different incoming depths at one block. Unreachable components are checked from depth zero so malformed dead code cannot bypass validation.

The six emitted call forms have no implicit x87 action. They preserve the incoming depth while their explicit operand or result conversion slots still apply. This matches final emission, where a call can carry a conversion and floating tracking is not reset at the call. `IC_RETURN_VAL`, `IC_RETURN_VAL2`, `IC_LEAVE`, `IC_RET`, and the final `IC_END` require depth zero after their own conversion action. Floating comparisons have one balanced x87 operation when `ICF_USE_F64` is set. `ICF_PUSH_CMP` and `ICF_POP_CMP` describe the separate machine-stack transfer used by chained comparisons and do not change abstract x87 depth. `HCIR0025` reports a live value at an exit boundary.

A successful verifier result is a distinct wrapper for later interpreter, optimizer, and backend entry points. Its `holyc-ir-x87-v1` trace lists each instruction's incoming and outgoing depth and every decoded slot in source order. This proves structural stack discipline only. It does not evaluate an operation, select an x87 encoding, or establish numerical identity between TempleOS and a hosted runtime.

## Verified integer-unary folding

`Holyc_lib.Ir_integer_unary_folding` accepts only an `Ir.X87_stack.t`. Callers cannot supply an unchecked sequence or block graph. `Compiler/OptPass012.HC:1-29,153-192` supplies the early-pass structure and the immediate rewrites for `IC_COM`, integer `IC_NOT`, and integer `IC_UNARY_MINUS`. `Compiler/OptLib.HC:17-23,196-225` supplies constant eligibility, result-class forwarding, source flag transfer, and producer removal. `Compiler/PrsExp.HC:608-616` maps `~`, `!`, and unary `-` to those opcodes; `Compiler/CInit.HC:27,50-52` fixes the zero-input immediate and one-input unary shapes; and `Compiler/OptPass789A.HC:449-459` supplies their 64-bit backend semantics.

This first pass uses a smaller eligibility rule than the mutable source optimizer. The producer must be a zero-flag `IC_IMM_I64` with an integer payload, one result, and a zero-depth internal `I64` or `U64` target. Its unary consumer must appear later in the same block, use that result exactly once across the graph, have no payload, carry zero flags, and produce one value. Complement accepts either word type and produces internal `I64`. Logical not preserves the operand word type. Unary minus accepts either word type and produces internal `I64`. Complement flips all 64 bits, logical not maps zero to one and every nonzero value to zero, and negation uses wrapping `int64` arithmetic, including `Int64.min_int`.

Canonical checked expression lowering supplies the unsigned unary-minus row directly. `Compiler/PrsExp.HC:679-685` gives a high-bit integer or character payload internal `U64`, and `Compiler/OptPass012.HC:180-192` changes unary minus over that exact zero-depth operand to internal `I64`. The emitted pair has zero flags, so `-0x8000000000000000` enters this pass and folds to one internal-`I64` immediate with the same bits.

The rewrite removes only the consumed immediate and changes the operator into `IC_IMM_I64`. The retained instruction keeps the operator's instruction ID, result ID, target type, and source span. Its operands become empty and its payload becomes the folded bits. The source-ordered block scan indexes each replacement as the current immediate, so a nested eligible chain reaches a fixed point during the same traversal. Running the pass again produces the same graph and an empty trace.

After planning every block, the module rebuilds the complete graph through `Ir.Block_graph.create` and reruns `Ir.X87_stack.verify`. It publishes the result only after both checks succeed; graph and x87 failures retain their structured child codes and identify the failed validation stage. The `holyc-ir-integer-unary-folding-v1` trace records each rewrite in block and source order with the removed instruction and value, retained instruction and value, original opcode, input bits, and folded bits.

Shared operands, flag-bearing candidates, other integer widths, public integer types, `F64`, malformed payloads, binary folding, general dead-code elimination, pass scheduling, persisted IR, interpretation, and machine emission remain outside this module. Cross-block value operands also remain outside it: `Ir.Block_graph.create` rejects such a graph with `HCIR0009` before an `Ir.X87_stack.t` can be constructed.

## Named function bodies

`Holyc_lib.Ir_function_body` wraps one checked graph in the metadata needed to identify a named HolyC function. The immutable value keeps a stable function ID, the function symbol and its declaration scope, a distinct function-body scope, return type, source-ordered parameter and local inventories, the stored `Ff_*` mask, a compiler-option snapshot, and optional source spans. Each parameter and local retains its semantic symbol, declared type, source position, and optional span. Positions are metadata from the owning declaration pass; the wrapper preserves list order and does not sort the inventory.

Construction accepts only a function symbol, parameter symbols and local-variable symbols from the body scope, nonnegative member positions, known stored flags, and known compiler options. It rejects `Ff_ARGPOP` combined with `Ff_NOARGPOP` and rejects `Ff_HASERRCODE` without `Ff_INTERRUPT`. Duplicate positions within either inventory and duplicate symbols across both inventories also fail. `HCIR0026` through `HCIR0033` cover these checks. The constructor runs x87 verification before returning and adds the function identity to any `HCIR0021` through `HCIR0025` failure.

The deterministic `holyc-ir-function-v1` form includes the pinned reference commit and embeds the graph body without a second schema header. It names all retained flags and options in their audited source order. This wrapper is a checked construction boundary for later lowering and execution. It does not create a graph from the frontend, calculate local storage, apply a calling convention, reconcile prototypes and definitions, or model TempleOS's separately compiled executable top-level statements.

## Executable top-level streams

`Holyc_lib.Ir_top_level_body` represents the separate code stream compiled by `Compiler/CMain.HC:LexStmt2Bin`. It retains a stable stream ID, source-item position, compiler-option snapshot, optional source span, checked graph, and verified x87 result. The type has no function symbol, declaration scope, parameters, locals, return type, or stored function flags because the pinned path does not create those facts.

`HCIR0034` rejects a negative stream ID. `HCIR0035` through `HCIR0037` cover a negative source-item position, invalid span, and option bits outside the checked compiler-option registry. X87 failures retain the stream and item context while keeping their existing `HCIR0021` through `HCIR0025` codes. The deterministic `holyc-ir-top-level-v1` dump embeds the graph body and records the pinned reference commit.

This is the container for one already-built statement stream. It does not lower an AST, decide whether the final expression produces a value, append `IC_RETURN_VAL2` or `IC_RET`, group streams into a module, or execute top-level code.

## Literal lowering

`Holyc_lib.Ir_literal_lowering` is the first checked instruction-producing boundary. The low-level `lower` entry point accepts one explicit literal payload, stable instruction and value IDs, and an optional span. `lower_expression` accepts a frontend expression and derives the payload and span from integer, character, F64, and string literal nodes through nested parentheses, unary plus, unary minus, logical not, bitwise complement, dereference, and address-of. `lower_typed_result` follows the checked operand result retained at each semantic wrapper, including dereference and address-of. The literal and every emitted prefix receive caller-owned instruction and value identities. All three paths construct accepted input through `Ir_instruction_sequence.create`.

The mapping follows `Compiler/PrsExp.HC:679-700`. Integer and character inputs produce `IC_IMM_I64`; a negative target value has internal type `U64`, while zero and positive values have internal type `I64`. F64 input is supplied as exact bits and produces `IC_IMM_F64` with internal type `F64`. Decoded string bytes produce `IC_STR_CONST` with internal type `U8 *`. The string payload does not gain a terminator or storage address at this stage.

`Compiler/PrsExp.HC:728-747` compiles a parenthesized term by entering `PrsExpression` for the inner value and adds no instruction for the parentheses. Lines 750-759 likewise consume unary plus without selecting an opcode. The hosted boundary therefore unwraps grouping and unary plus iteratively, preserves the inner literal span, and produces the same instruction as the direct form. Neither transparent wrapper receives an IR identity.

`Compiler/PrsExp.HC:614-675` selects `IC_COM`, `IC_NOT`, `IC_UNARY_MINUS`, `IC_DEREF`, and `IC_ADDR`; lines 133-162 add them after the operand. `Compiler/CInit.HC:49-53` fixes their one-argument, one-result shapes. The lowerer keeps the literal instruction and adds checked prefix instructions from innermost to outermost. Each uses the preceding result as its operand and retains the operator token span. The pinned parser initially forwards the current type through all three numeric unary operations. The parser-backed `lower_expression` entry point preserves that insertion-time type for unary minus and logical not but applies the optimizer-visible internal `I64` complement correction already owned by the hosted boundary. The checked `lower_typed_result` entry point instead uses each semantic node's exact type: a high-bit internal-`U64` leaf stays `U64`, and unary minus over that zero-depth operand becomes internal `I64`. Dereference removes one pointer class when present and otherwise keeps the operand class. Address-of adds one pointer layer. When it immediately follows dereference, the lowerer removes that dereference and lets `IC_ADDR` consume the earlier operand, matching `OptFree` at `PrsExp.HC:153-158`. Folding remains outside this boundary.

Callers provide instruction and value identities in emitted inner-to-outer order, after address-of cancellation. `HCIRL0001` rejects a missing or excess identity before an unchecked sequence can escape. `HCIRL0002` rejects address-of when the selected result would exceed the checked four-layer pointer limit. For a nonliteral expression wrapped only in supported prefix nodes, `lower_expression` returns `Not_literal` without constructing IR. Semantic traversal identities are not reused as IR identities.

`holyc-ir-literal-v1` records the source kind, result type, checked instruction chain, source spans, and pinned reference commit. `lower_typed_result` copies those facts from a payload-bearing semantic leaf through nested parentheses, unary plus, unary minus, logical not, bitwise complement, dereference, and address-of without consulting a frontend AST node. Address-of cancels an immediately inner dereference before the caller's identity count is checked. The address instruction remains, consumes the earlier operand, and keeps the address operator span. Update prefixes, multi-operand expression graphs, string storage, unary folding, and nonliteral roots remain outside this boundary.

## Checked expression lowering

`Holyc_lib.Ir_expression_lowering` accepts one checked semantic result and starting instruction and value IDs. It first validates the complete accepted tree with an explicit worklist. Only after that plan succeeds does it allocate identities, lower integer, character, `F64`, or string leaves through the literal module, and emit operations in postorder. A binary parent consumes its source-left child before its source-right child. A unary operation follows its one operand. The returned value contains one verified sequence, its result value and type, and the next unused identities. Callers cannot supply a precomputed node count or individual IDs.

Direct and transparently grouped string leaves follow `Compiler/PrsExp.HC:692-697`, where the parser creates `IC_STR_CONST` with the decoded bytes and the internal `U8` pointer class. `Compiler/LexLib.HC:248-285` supplies those bytes and their length, and `Compiler/CInit.HC:29` records a zero-argument, one-result instruction that is not a foldable constant. The lowerer requires the checked internal `U8 *` type at pointer depth one, integer result class, address value category, and zero array rank. It then emits one zero-operand `IC_STR_CONST` with the exact bytes, leaf span, zero flags, and consecutive module-owned identities. Grouping aliases that one value and consumes no identity. This boundary neither appends a terminator byte nor allocates storage. Conversion-bearing and otherwise unsupported surrounding operations return `Unsupported_expression` before a sequence is exposed.

Completed function-body and executable top-level aggregate offset paths follow `Compiler/PrsExp.HC:353-381`. `PrsOffsetOf` starts at zero, adds each `CMemberLst.offset`, advances through the selected member class, and passes the final sum to `ICAdd` as an internal-`I64` `IC_IMM_I64`. The lowerer consumes the semantic path retained before this boundary. It requires a source location, zero-depth internal `I64` result, integer class, offset category, zero array rank, and at least one resolved member segment. The retained final value must equal the last cumulative segment. Direct paths and standalone `offset(...)` source nodes both emit one zero-operand immediate with that byte value, exact expression span, zero flags, and consecutive identities. A standalone root may be an aggregate publication or a checked zero-rank by-value aggregate object; the latter keeps its exact specialized query and type evidence. Parameters, automatic and static locals, checked globals, and executable top-level module globals share this path. Grouping, integer arithmetic, mixed `F64` producer conversion, and expression-statement termination reuse the ordinary worklist in JIT and AOT mode. The lowerer does not repeat member lookup or layout arithmetic, calculate a runtime address, read storage, or accept ordinary object-member access.

Issue #494 extends the checked path shape to function-body expressions, including exact publication and current-or-base lookup evidence. Issue #496 verifies that the owner-neutral planner consumes those results with the same metadata checks and instruction shape already used for executable top-level paths. Function-body grouping, numeric composition, mixed `F64` producer flags, and `IC_END_EXP` now have direct regression coverage in both modes.

Direct function addresses use a private atomic plan node rather than the generic `IC_ADDR` unary path. `Compiler/PrsExp.HC:621-654` selects three instruction shapes from the exact declaration state: a resolved JIT function becomes `IC_IMM_I64`, a resolved AOT function becomes `IC_ABS_ADDR`, and an unresolved JIT extern becomes `IC_IMM_I64` followed by `IC_DEREF`. `Compiler/CInit.HC:27,30,53` supplies their operand and result shapes, and `Compiler/CompilerA.HH:30,33,60` fixes their identities. The planner accepts only an address-of result and direct-function operand whose declaration, canonical symbol, path, origin, checked type, value category, and zero array rank agree. It then gives `IC_IMM_I64` or `IC_ABS_ADDR` the canonical symbol payload. The extern-slot `IC_DEREF` consumes the immediate result and carries no payload. All produced values keep the internal zero-depth `RT_PTR` type, and every instruction keeps the exact `&` operator span. Flags are zero except for checked root conversion on the final producer; direct-call composition adds `ICF_PUSH_RES` to that same producer. Function-body and executable top-level results share the path. `HCIRL0004` rejects incomplete or inconsistent retained evidence before a sequence is exposed, and `HCIRL0005` reports instruction or value identity exhaustion. Ordinary object and callback addresses and bare function values remain unsupported. The symbolic fragment does not resolve a numeric address, access a runtime slot, create an import, relocation, or fixup record, execute an instruction, or emit machine code.

The accepted binary operators are `IC_SHL`, `IC_SHR`, `IC_MUL`, `IC_DIV`, `IC_MOD`, `IC_AND`, `IC_OR`, `IC_XOR`, `IC_ADD`, `IC_SUB`, the six comparisons, `IC_AND_AND`, `IC_OR_OR`, `IC_XOR_XOR`, and `IC_POWER`. `Compiler/CInit.HC:60-84` assigns each form two arguments and one result. `Compiler/PrsExp.HC:15-61,167-255` establishes source-term emission and precedence completion. `Compiler/OptPass012.HC:40-61` and `Compiler/OptPass3.HC:68-88` fix the right and left tree slots later consumed by the optimizer. The hosted sequence keeps source order as operand zero then operand one. Every operator except power accepts checked integer operands with an integer result; modulo, the six comparisons, and power also accept the floating domains described below.

`IC_UNARY_MINUS`, `IC_NOT`, and `IC_COM` may occur at any depth in that tree. `Compiler/PrsExp.HC:133-162,614-675` selects each opcode and inserts it after its operand. `Compiler/CInit.HC:49-53` assigns one argument and one result. `Compiler/OptPass012.HC:153-192` preserves logical-not types, changes complement to internal `I64`, and changes unary minus over an exact zero-depth internal `U64` operand to internal `I64`; other accepted unary-minus types remain unchanged. The lowerer requires that exact matrix and does not accept a stale internal-`U64` result for the special case. Immediate folding remains optimizer work. Every unary instruction retains its own operator span.

`IC_DEREF` and `IC_ADDR` may wrap any accepted subtree. `Compiler/PrsExp.HC:151-158` removes one pointer class for dereference when present, adds one for address-of, and calls `OptFree` when address-of sees an immediately preceding dereference. The lowerer performs that cancellation while planning the tree, before allocating an identity. It omits the dereference, retains `IC_ADDR` and its operator span, and makes that address consume the canceled dereference's operand value. Parentheses and unary plus between the two operations remain transparent. A dereference outside an address remains a separate instruction.

Pure `F64` trees accept `IC_MUL`, `IC_DIV`, `IC_MOD`, `IC_ADD`, and `IC_SUB`. `Compiler/OptLib.HC:92-178` resolves these operations to `FBO1_F64` when either forwarded operand class is floating. `Compiler/OptPass012.HC:435-455` retains or folds floating modulo, and `Compiler/OptPass789A.HC:530-534` selects `ICFMod` when `ICF_USE_INT` is clear. Unary plus remains transparent; unary minus and logical not retain the checked `F64` type. Literal bits pass through unchanged, and division or modulo by a literal zero remains an ordinary instruction because this boundary does not evaluate it.

Mixed integer/`F64` trees accept the same five arithmetic operations. `Kernel/KernelA.HH:1602` defines `ICF_RES_TO_F64`, and `OptFixupBinaryOp1` applies that intent to a non-floating producer when the combined class is `F64`. The checked lowerer places the bit on the final instruction of each integer operand subtree. Parentheses and unary plus pass the request to the retained producer. Earlier nodes in the integer subtree keep zero flags. The canonical pre-optimizer form also leaves an integer literal as `IC_IMM_I64` with its exact integer payload and the conversion bit; `OptFixupBinaryOp1` later rewrites such an immediate to `IC_IMM_F64`. The lowerer does not perform that numerical conversion.

Fixed call parameters use the same producer boundary in both directions. `Compiler/PrsExp.HC:470-484` compares each provided argument's forwarded class with the fixed parameter after expression optimization and sets either `ICF_RES_TO_F64` or `ICF_RES_TO_INT` on the argument's final producer. Checked function-body and executable top-level argument roots now retain that comparison. Canonical lowering seeds its worklist from the root intent, applies `ICF_RES_TO_F64` only to an integer producer and `ICF_RES_TO_INT` only to an `F64` producer, and rejects incompatible evidence before allocating identities. Parentheses and unary plus forward the request without adding an instruction. Literal payloads and composite operand links remain unchanged; numerical conversion and call construction remain later work.

`IC_SHL` and `IC_SHR` also accept pure and mixed floating domains with an internal-`F64` result. `Compiler/OptPass012.HC:229-266` passes both operations through `OptFixupBinaryOp1`, folds a constant floating pair to `IC_IMM_F64`, or retains the selected class. Canonical lowering leaves the shift instruction unflagged and places `ICF_RES_TO_F64` on each integer operand producer. A complete integer shift subtree can be that producer. Evaluation, `IC_SHL_CONST` or `IC_SHR_CONST` rewriting, and the `ICShift` consumer at `Compiler/OptPass789A.HC:506-516` remain later stages.

`IC_AND`, `IC_OR`, and `IC_XOR` accept the same pure and mixed floating domains with an internal-`F64` result. `Compiler/OptPass012.HC:458-483` passes each operation through `OptFixupBinaryOp1`; a constant floating-domain pair folds its raw 64-bit payload into `IC_IMM_F64`, while a nonconstant operation retains its selected class. Canonical lowering leaves the bitwise instruction unflagged and records `ICF_RES_TO_F64` only on an integer operand producer. A complete integer subtree can be that producer. Raw-bit evaluation, folding, and the consumers selected at `Compiler/OptPass789A.HC:536-549` remain later stages.

The three logical binary opcodes also accept two `F64` operands or a mixed integer/`F64` pair. `Compiler/OptPass012.HC:693-713` passes each operation through `OptFixupBinaryOp1`, folds constant operands when permitted, and then assigns internal `I64` to the result. Canonical lowering keeps that result type, places `ICF_RES_TO_F64` on an integer operand producer, and leaves `IC_AND_AND`, `IC_OR_OR`, or `IC_XOR_XOR` unflagged. A nested logical result can itself carry the conversion bit when an outer floating-domain operation consumes it. This boundary neither evaluates truth nor constructs the branch forms selected by `OptBrZero` and `OptBrNotZero`.

The six comparison opcodes accept two `F64` operands or one integer and one `F64` operand. `OptFixupBinaryOp1` selects the floating operand class and applies the same producer-side conversion intent. `Compiler/OptPass012.HC:724-823` then sets `ICF_USE_F64` on a nonconstant floating comparison and gives an ordinary comparison result the internal `I64` class. The canonical lowerer records both facts directly: the comparison instruction carries `ICF_USE_F64`, each integer operand subtree root carries `ICF_RES_TO_F64`, and the result remains internal `I64`. If that Boolean feeds later floating arithmetic, its comparison instruction carries both bits. Lowering does not fold the comparison or reproduce the optimizer's comparison-to-zero rewrite. The x87 verifier treats `ICF_USE_F64` as one balanced comparison operation.

`IC_POWER` accepts any pair of checked integer or `F64` operands and always produces internal `F64`. `Compiler/CInit.HC:64,288` records two arguments, one result, no implicit floating-stack pop, and right association. `Compiler/OptPass012.HC:299-305` places `ICF_RES_TO_F64` on every integer operand producer, including both sides of an integer-only power. The canonical form retains those producer flags and leaves `IC_POWER` itself unflagged; its dedicated floating implementation does not use the comparison-only `ICF_USE_F64` bit. The checked tree already preserves `PrsExp`'s rule that unary minus follows the completed power. Lowering does not fold the operation, call `SYS_POW`, or evaluate a result.

Checked primitive numeric postfix casts use the same worklist. `Compiler/PrsExp.HC:1017-1055` changes the preceding operand class and appends `IC_HOLYC_TYPECAST`; `Compiler/CInit.HC:48` gives the instruction one argument and one result. The lowerer emits the operand first, then a cast whose target is the checked public primitive type. The cast keeps the full source span instead of only the target tokens. Its integer payload reproduces `PrsUnaryModifier`'s `was_paren` value: one when the immediate source operand is an ordinary parenthesized expression, zero otherwise. Nested casts therefore retain one instruction per source cast. When a cast is the integer producer consumed by mixed floating arithmetic, that cast carries `ICF_RES_TO_F64`. `OptPass012.HC:87-110` owns immediate folding and any later removal or class transfer; this lowerer performs neither.

Bound scalar and aggregate values are available through the function-body semantic path; unbound primitives also work in executable top-level statements. ## Checked expression-statement termination

## Checked executable top-level bodies

`Holyc_lib.Ir_top_level_statement_lowering` places one checked ordinary expression statement or standalone direct-call statement into an executable top-level stream. Successful lowering returns the checked body and the next unused instruction and value identities. Supported ordinary values include the numeric expression slice, current position, resolved `defined`, primitive `sizeof`, and checked aggregate offsets already accepted by the expression lowerer. Unsupported values or calls, mismatched evidence, invalid options, and identity exhaustion expose no partial sequence, graph, or body. Control flow, implicit output, callbacks, `IET_MAIN`, interpretation, and machine emission remain later work.

`Holyc_lib.Ir_top_level_batch_lowering` repeats that boundary for source-ordered statement lists. `lower_direct_calls` requires equal-length standalone-call, classified-target, and compiler-option lists. `lower_expressions` requires equal-length ordinary-expression and compiler-option lists. `lower_mixed` instead accepts the complete checked statement stream, a separately ordered target list, and one compiler-option snapshot per statement. Mixed target assignment is independent of target-list order. A statement is eligible only when it has one expression-statement root. A classified target must match both that root's semantic result ID and the exact physical root-expression object. The root is considered a standalone direct call only when the exact call is the root, its callee form is an identifier, and its retained module publication is a function. Calls nested inside a larger expression and global or outer callback calls do not satisfy that rule; without an assigned target they continue through ordinary expression lowering. Missing, duplicate, foreign, unrelated, unmatched, and ambiguous targets return no body list, as do invalid option snapshots, unsupported child lowering, verifier failures, and exhausted stream, block, instruction, or value identities. ## Current boundary

The checked sequence, control-flow table, block graph, opcode-potential effect table, x87 verifier, named-function body, executable top-level stream, literal lowerer, limited expression lowerer, expression-statement terminator, goto-label fragment, and break fragment remain an incomplete compiler pipeline. A named body carries return, parameter, local, function-flag, and compiler-option facts. A top-level stream instead carries its source-item position and compiler-option snapshot. The literal path can construct a checked immediate or string constant from an explicit payload, a parser node, or a typed semantic leaf, including nested parentheses, unary plus, unary minus, logical not, bitwise complement, dereference, and address-of. Both parser and typed unary paths emit inner-to-outer instruction chains and assign every typed instruction the exact checked type of its semantic node. Complement results use internal `I64`; address-of adds a pointer layer and applies the pinned immediate-dereference cancellation rule. Dereference is represented but not executed. The expression path accepts integer and character leaves beneath transparent grouping and unary plus, composes all five implemented prefixes, and emits the audited two-operand integer operations in postorder. It also accepts ordinary current-position leaves as typed `IC_RIP` producers, pure `F64` literal trees, mixed integer/`F64` arithmetic and comparisons, and every checked integer/`F64` pair under `IC_POWER`; pure floating trees additionally compose unary minus and logical not. Mixed operations record `ICF_RES_TO_F64` on integer producers, floating comparisons also record `ICF_USE_F64` and retain internal `I64` results, and power retains an internal `F64` result without an operation flag. The lowerer does not execute a conversion, evaluate a floating operation, or perform the optimizer's immediate rewrite. Accepted ordinary function and executable top-level expression statements append `IC_END_EXP` with the complete statement span and unused-result flag. Resolved language labels receive stable block identities and source-ordered `IC_LABEL` or `IC_JMP` fragments. Resolved break regions likewise receive stable block identities and source-ordered `IC_JMP` fragments. Neither boundary partitions or places a full statement stream. Pointer-typed results remain limited to address, dereference, and ordinary current position; pointer arithmetic and storage are not claimed. Concrete RIP selection is also not claimed. These forms do not yet carry exception or lock regions, memory regions, relocations, an ABI layout, or linkable module ownership. There is no general statement lowerer, optimizer pipeline, interpreter, or backend consumer. Payload validation is complete only for control-flow targets, audited floating flags, and the implemented expression constructors. No compatibility result on this page implies that a HolyC program can be lowered or run.

The limited expression path also accepts exact direct-function addresses in both result owners. Their symbolic one- or two-instruction fragments preserve the checked path, canonical symbol, internal `RT_PTR` type, address-of operator span, and final-producer flags. They do not broaden ordinary object or callback address support, turn a bare function into a value, or add runtime address resolution, slot access, relocation records, execution, or machine emission.

The semantic frontend now assigns immutable typed results to provided fixed and variadic expressions on resolved direct and typed callback calls. Those records keep source expression identity, type, value category, and forwarded class, but they are not IR values. A nested resolved direct or indirect call additionally retains its call-resolution identity and the source-visible return type. A selected declared default has a separate semantic record: it keeps the exact parameter and default-use identity, checked parameter type, forwarded class, ordinary-expression or `lastclass` kind, and the immediate or AOT string-constant path selected by compilation mode. It deliberately has no expression ID because no call-site expression was provided. Fixed expression results can carry a target conversion decision; a `lastclass` default can also carry the preceding provided result and derived base spelling; variadic results retain only their actual class. Ordinary function expression statements keep the same checked result plus unused-result intent. Accepted numeric statements now turn that intent into `IC_END_EXP`; other statement values remain semantic records only. Implicit-output statements retain the intent alongside the synthetic `Print` or `PutChars` target, fixed-source form, and checked output arguments. A downstream semantic result identifies the source-visible module header and canonical target or the exact outer-table entry. Function and executable top-level conditions keep the same typed result plus an `if`, `while`, `do while`, or `for` role. Accepted numeric conditions from either owner can now append a source-selected branch to a caller-owned target. The remaining paths do not create calls, output conversions, Boolean conversions, blocks, or labels. None has a complete use list, block placement, evaluated default payload, side-effect model, relocation intent, string allocation, or machine representation. Later M5 work must consume each semantic result without treating its deterministic traversal ID or call index as an instruction ID.

The same source view gives ordinary `defined` a checked operand record instead of a nameless marker. The semantic evaluator distinguishes a name token from punctuation, replays the spelling at its exact source point, and stores the selected local, module, or outer evidence—or an explicit complete-chain miss. Supported results then enter the existing integer-immediate lowering path.

Ordinary `sizeof` has a separate checked semantic leaf rather than sharing the generic unsupported-expression marker. It retains the keyword and complete expression origins, balanced wrapper parentheses, root spelling and exact source-ordered function or top-level query, every member segment, and contiguous pointer layers. Generated components keep both invocation and definition provenance. The constructor and owning tree reject a query with the wrong role, spelling, origin, function, or statement.

An unbound public primitive root receives the byte size audited from `Compiler/CInit.HC`. One or more pointer layers select the eight-byte `RT_PTR` storage established by its pinned `RT_I64` alias. Local, module, and supplied outer records are checked first, so a source binding with a primitive spelling prevents this built-in classification. Function-body aggregate roots and members additionally carry completed layout evidence from the immutable member index. Each lookup records the queried and declaring aggregate, inheritance depth, member identity, checked member type, and full layout size. Constructor validation rejects a member spelling, queried aggregate, or segment type that disagrees with the retained root and prior lookup. The expression lowerer validates the existing internal-`I64` object result, then emits one zero-operand `IC_IMM_I64` with the checked byte payload and complete expression span. Grouping and mixed `F64` arithmetic use the same conversion path as other integer producers. Root array extents, pointer traversal, top-level aggregate roots, unmappable outer aggregates, and function debug ranges remain unsupported and produce no partial sequence.

Here, an operand graph means an IR operand and use graph. Semantic parentheses, prefix operators, and postfix casts retain one exact checked child. A nested cast points to its immediate cast result; grouping and binary operands remain explicit intermediate semantic nodes. A completed semantic binary result retains its exact checked left and right children in source order, including any conversion-bearing replacement produced while checking an assignment. These child links do not allocate instructions, blocks, uses, or values. The limited expression lowerer consumes them for its documented integer, pure `F64`, mixed arithmetic, comparison, power, current-position, address, dereference, primitive postfix-cast, and binary shapes. Executable top-level switch selectors are also contextual semantic records, not IR values. Executable top-level switch cases remain on the semantic side of the same boundary. An explicit `return` under executable top-level code is rejected before this semantic tree can be built. Switch cases remain semantic patterns at this stage. An implicit label has no fabricated expression. A single label has one checked value, while a ranged label keeps its checked start and end together.
